# 家翻新数据库表设计（Prisma + NestJS）

## 1. 设计说明

本设计依据当前 `jfx-web` 前端页面、`src/types` 中的业务字段以及《后台管理系统设计.md》整理，目标是先支撑现有业务闭环，并尽量减少表数量和过度抽象。

约定：

- 示例按 MySQL 设计，金额统一使用 `Decimal(10, 2)`，禁止使用浮点数存金额。
- 数据库表名、字段名使用 `snake_case`，Prisma 模型和字段使用驼峰命名。
- 手机号、地址、订单金额等历史信息在订单中保存快照，避免用户修改资料后影响历史订单。
- 图片上传后只在数据库保存 URL；多个图片、标签、案例亮点、规格参数等使用 `Json`。
- 所有业务状态使用 Prisma Enum 固定，后台字典只控制普通展示选项，不控制核心状态流转。
- 普通业务数据原则上不物理删除，通过 `status`、`isEnabled` 或 `deletedAt` 控制。

## 2. 简化原则

本期不建立以下独立表：

- 工作台统计表：直接聚合用户、预约、项目和订单数据。
- 员工业绩表：从装修项目的负责人、成交金额、完成时间实时统计。
- 分类层级表：案例分类和焕新空间分类需要独立维护，但当前均为单层分类，不设计父子层级；只有商品分类保留树形结构。
- 案例图片、费用、亮点、方案图片、商品相册表：统一保存为 `Json`。
- SKU 表：当前仅要求简单 SKU，规格名称、规格值和商品编码直接保存在订单明细或商品字段中。以后出现多规格独立库存时再拆表。
- 支付单、退款单、订单状态历史表：当前支付及退款字段直接放在商品订单中；对关键变化写操作日志。
- 积分账户表：积分余额及累计值直接放在用户表，积分变动放流水表。
- 消息模板表：模板标识、发送内容和发送结果合并为消息记录；模板变多后再拆分。
- 客户标签、服务区域、角色权限关联表：现阶段使用 `Json`，避免过早建立大量中间表。

// 用户表：保存客户和员工共用的登录账号及会员资产汇总
model User {

  /// 分享标题

## 5. 关键实现要求

### 5.1 编号生成

`userNo`、`employeeNo`、`appointmentNo`、`projectNo`、`orderNo`、`serviceNo` 和 `feedbackNo` 建议由 NestJS 服务统一生成，例如：

- 用户：`U202608050001`
- 预约：`AP202608050001`
- 装修项目：`RP202608050001`
- 商品订单：`PO202608050001`
- 安装服务单：`IS202608050001`

不要使用数据库自增 ID 作为对外展示编号。

### 5.2 必须使用事务的操作

- 商品下单：创建订单、创建明细、扣库存、写库存流水、锁定优惠券、扣积分。
- 订单取消：变更订单状态、释放库存、退回优惠券和积分。
- 支付回调：校验幂等、更新支付状态和实付金额、生成安装服务单。
- 积分调整：更新用户积分汇总字段并写入积分流水。
- 优惠券领取：校验发行数量、每人限领数量并创建用户券。

### 5.3 状态校验

状态不可由前端任意覆盖，应在 NestJS Service 中实现允许的流转：

- 装修预约：`PENDING_CONTACT → PENDING_VISIT → COMPLETED`
- 装修项目：`PENDING_CONFIRM → IN_SERVICE → COMPLETED`
- 商品订单：`PENDING_PAYMENT → PENDING_INSTALLATION → IN_SERVICE → COMPLETED`
- 安装服务：`PENDING_APPOINTMENT → PENDING_ASSIGNMENT → PENDING_VISIT → IN_SERVICE → COMPLETED`
- 意见反馈：`PENDING → PROCESSING → REPLIED → CLOSED`

取消、退款属于分支状态，需额外校验支付、库存、优惠券和积分是否需要回退。

### 5.4 密码与隐私

- `User.password` 和 `Admin.password` 只保存 Argon2 或 bcrypt 哈希，不能保存明文。
- 手机号、详细地址、操作前后数据属于敏感数据，接口根据管理员权限脱敏。
- 价格、库存、积分、状态、负责人和权限变化必须写入 `OperationLog`。
- `permissions` 与 `dataScope` 使用 Json 是为了简化首期实现；若后续需要管理员多角色、复杂按钮授权，再拆为 `Role`、`Permission` 和关联表。

## 6. 后续按需扩展

只有出现明确需求时再增加以下结构：

1. 商品多规格：新增 `ProductSku`，并将库存、价格和订单明细关联到 SKU。
2. 多仓库存：新增仓库、库存、入出库单和库存批次表。
3. 复杂权限：新增角色、权限、管理员角色、角色权限四张表。
4. 多次支付或部分退款：新增支付单和退款单。
5. 审批流程：新增审批单和审批节点记录。
6. 精细化消息模板：将模板定义与发送记录拆分。

当前版本优先保证预约、装修项目、商品订单、安装、库存、积分和优惠券形成完整闭环，不提前建设上述复杂能力。
