## 仍未完成及具体问题

### P0：交易完整性与已有流程收口

1. **恢复正式支付金额并核对回调金额。** `jfx-api/src/payment/payment.service.ts` 的微信请求仍写死 `total: 1`；`src/notify/notify.repository.ts` 的订单应付与回调金额一致性判断被注释。这是明确的测试阶段实现，真实金额验收必须先处理。
2. **补订单继续付款和客户端取消。** 小程序订单列表和详情对应按钮仍调用“功能建设中”；取消后端及管理端已存在，应接入现有取消接口。继续付款需要按已有订单重新获取支付参数，不能再次创建订单。
3. **补创建订单的幂等与失败恢复。** 后端先提交订单及资源占用，再请求微信预支付；后一步失败时订单已存在。当前 DTO 没有请求幂等键，前端将部分 400 视为可修正重试，不能保证跨页面/网络重试不重复建单。需要可恢复的订单标识、重试协议及未支付超时关闭/资源返还机制。
4. **统一券规则与刷新。** 前端 `order-discounts.ts` 和券页要求模板为 PUBLISHED，并同时检查模板 validTo；后端允许停用模板的已领券继续使用，有效期按领券 expiresAt。需明确统一口径。券页 onShow 目前仅更新时间，没有主动刷新用户券数据。
5. **统一业务失败处理。** `src/utils/http.ts` 遇到 HTTP 2xx、业务 code=400 仍 resolve；仅 await 后提示成功的调用可能误判。统一处理业务错误后应复核现有写入口。
6. **修复管理端订单总页数。** `jfx-api/src/order/order.service.ts` 的 findAll 使用 `Math.ceil(total / Number(query.pageNum))`，应按 pageSize 计算；小程序用户订单接口对应计算正常。
7. **补方案预约服务端防重复。** PLAN 创建目前直接 create，缺少 CASE 已有的同类重复约束；同时补客户装修项目“已取消”独立筛选（当前可从全部查看）。

验收重点：真实订单金额、支付取消后恢复、预支付失败后重试、重复回调、订单取消与支付竞态、库存及券积分只占用/返还一次；装修三类预约分别覆盖提交至建项/确认/完工和取消路径。
